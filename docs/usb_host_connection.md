# Почему DiCE не коннектится на хосте (но работает в XP-виртуалке)

**РЕШЕНО: удаление и повторная установка драйвера DiCE
(`DiceUsb.inf` из `C:\Program Files\DiCE\Tools\Driver`) вернули коннект
J2534 на хосте.** Корень — дефект установки драйвера: устройство
«поднималось» (Started), но WinUSB-интерфейс в формате, который ждут
DLL (`.#{GUID}\INTERFACE_0x00\PIPE_0x0`), не создавался. Преходящего
состояния после reset на самом деле не было — интерфейс не поднимался,
пока драйвер не переустановили.

Инцидент 22.09.2026. Симптом: `PassThruOpen()` в `TSDiCE64.dll` падает:

```
UsbHardware::Open() failed, could not open read end point.
GetLastError() = 3  (ERROR_PATH_NOT_FOUND)
```

Одинаково на старом и новом .mot → **прошивка ни при чём**.

> **Корректировка (после проверки): VirtualBox НЕ причина.** ВМ не
> запущены, VBoxUSB STOPPED, процессов VBox* нет; `VBoxUSBMon` — просто
> загруженный ядро-фильтр, без ВМ он устройство не забирает. Активные
> USB-фильтры 17AA:D1CE в трёх XP-ВМ — потенциальная помеха только
> **при запуске ВМ**, не в момент инцидента.
>
> **Вторичная корректировка (промежуточная):** после инцидента оба
> интерфейса стали Enabled и `CreateFile` по путям `\\?\USB#...#{GUID}`
> — OK. Сначала это выглядело как преходящее состояние, но реальное
> лечение оказалось **переустановкой драйвера** (см. заголовок) — т.е.
> установка драйвера была дефектной/зависшей, и состояние «Started»
> само по себе не гарантирует рабочий WinUSB-интерфейс.

## Подтверждение: прошивка исправна

Запуск DiCE **в Windows XP (VirtualBox)** с обновлённой прошивкой —
коннект J2534 проходит нормально. Дополнительно из `FwdlApp.exe.log`
(17:48): полный цикл по USB на хосте ещё **до** деградации отработал:
`RfcOpen()=0`, версии прочитаны (HW 1.4.3, FW 5.6.2, bootl 5.0),
стирание/запись/проверка — «Device update OK!». Повторный open после
reset устройства уже не шёл.

## Что реально сломано на хосте

1. Устройство Windows видит: `USB\VID_17AA&PID_D1CE\DiCE-206751`
   (SETEK AB, class «DiCE Hardware», статус **Started**), ядро
   `DiceUsb.sys` (KMDF 1.9, **2011**) — RUNNING.
2. Устройство публикует **два интерфейса** (class «DiCE Hardware»):
   GUID `4e8a43b0-259a-43c2-a025-baee43c02571` и `a5dcbf10-...`. В
   момент проверки они **Enabled** и открываются:
   - `\\?\USB#...#{4e8a43b0-...}` → OK;
   - `\\?\USB#...#{a5dcbf10-...}` → OK.
3. **Но** обе DLL (`TSDiCE64.dll`, `RfcFWDL32.dll`) открывают интерфейс
   в **WinUSB-формате**: `.#{4e8a43b0-...}\INTERFACE_0x00\PIPE_0x0`
   (и `\\.\{GUID}\...`). Этот путь сейчас **не существует**
   (`CreateFile` → **err=3 = ERROR_PATH_NOT_FOUND**) — ровно тот код,
   что в логе. Т.е. драйвер создаёт «сырой» интерфейс, а не WinUSB-обёртку
   с `\INTERFACE_x\PIPE_x`, которую ждут DLL.
4. В `.mot` USB-дескриптор устройства: class FF/00/00, **1 интерфейс**,
   EP 0x81 (IN, 64 B) / 0x01 (OUT, 64 B), строки «DiCE Automotive
   Adapter».

## VirtualBox (проверено — НЕ причина)

- ВМ не запущены, VBoxSVC отсутствует, `VBoxUSB` STOPPED, процессов
  `VBox*` нет. `VBoxUSBMon` RUNNING — это постоянный ядро-фильтр
  USB-стека VirtualBox; без активной ВМ он устройство не забирает.
- **Но** три XP-ВМ имеют **активные** USB-фильтры `17AA:D1CE`
  («Неизвестное устройство 17AA:D1CE [0100]») — при следующем запуске
  любой из них VirtualBox заберёт DiCE у хоста.
- В PnP-базе есть «отвалившийся» инстанс
  `USB\Vid_80EE&Pid_CAFE\DiCE-206751...` (VirtualBox USB Driver,
  Disconnected) — след прошлой привязки к ВМ.
- Виртуалка — рабочая альтернатива подключения (проверено), а не
  источник поломки хоста.

## Почему в XP-виртуалке работает

Пакет драйвера `DiceUsb.inf` собран **под XP SP2 (32-bit) и Vista
(64-bit)**: `CatalogFile.NTx86=dicex86.cat`, `NTAMD64=dicemd64.cat`.
32-битный вариант в XP работает штатно. На современном 64-битном хосте
старый x64-драйвер (2011, KMDF 1.9) устройство «поднимает»
(Started/RUNNING), но интерфейс не экспонирует — DLL его не находит.

## Лечение (проверено — сработало)

**Удаление и повторная установка драйвера DiCE** (Device Manager →
DiCE → Uninstall, затем установка `C:\Program Files\DiCE\Tools\Driver\DiceUsb.inf`,
или `pnputil /add-driver ... /install` + Disable/Enable устройства) →
коннект J2534 на хосте восстановлен.

На будущее, если «could not open read end point» / err=3 вернётся:

1. Сначала — переустановка драйвера (рекуррентная причина, проверено).
2. Выдернуть/вставить USB-кабель (полная пере-перечислизация).
3. Перед запуском любой XP-ВМ **снять USB-фильтры 17AA:D1CE**
   (VirtualBox → Settings → USB), иначе VirtualBox заберёт устройство.
4. Проверка состояния:
   `pnputil /enum-devices /connected /instanceid "USB\VID_17AA&PID_D1CE\DiCE-206751@000000000000" /interfaces`
   — оба интерфейса должны быть **Enabled**.

## Примечания

- БТ-вариант подключения («Volvo/Ezurio/Laird USB Bluetooth adapter»)
  на этом хосте не работает: штатного BT-адаптера нет; COM12/COM13 —
  это сопряжённый HC-05 (BT-модуль CH05), не интерфейс DiCE.
  > Уточнение 22.09.2026: COM12 в системе **нет** (`SerialPort::GetPortNames()`
  > → COM3, COM4, оба — SPP-сервисы других устройств); у сопряжённого DiCE
  > SPP-COM-порта нет вообще. `Comport` в реестре не читает ни одна из DLL
  > (строки `Comport`/`COM%d` в них отсутствуют) — BT идёт сокетом по адресу.
- `pt2500Csm.exe` и `fdlauncher` в процессах — посторонние, к DiCE
  отношения не имеют (проверено: ни один процесс DLL DiCE не держит).

## Рецидив 22.09.2026 20:19 и лечение в этот раз

Тот же симптом: `UsbHardware::Open() failed, could not open read end point`,
`GetLastError()=3`, при том что устройство в PnP — **Started**, драйвер
`oem68.inf` (DiceUsb, RUNNING), а пути
`\\?\usb#vid_17aa&pid_d1ce#dice-206751@000000000000#{4e8a43b0-...}\INTERFACE_0x00\PIPE_0x0`
(и вариант с `\\.\`) **открываются из стороннего процесса**. Контрольные
варианты без суффикса `@000000000000` и с чужим GUID дают ровно **err=3** —
т.е. ошибка означает «такого пути нет», а не «нет доступа».

Простая переустановка `DiceUsb.inf` в этот раз **не помогла**: после неё в
20:23 тот же err=3. Вылечило **удаление драйверов + чистка реестра +
установка заново** (SetupDiCE) — после этого `PassThruOpen` по USB прошёл за
6 мс (`PassThruReadVersion` = 5.6.2, HW 1.4.3, VBATT ≈ 12.8 В).

Что переустановка сбрасывает (проверить после неё):

- `LogFile` → `C:\Program Files\DiCE\Tools\TSDice32.log` (в 64-битном ключе!);
- `FwdlApplication` → `...FwdlApp.exe -file "C:\Program Files\DiCE\Tools\dice_5_6_2.mot"`
  — дефолтная прошивка **заводская**; при прошивке патча всегда указывать
  `-file` явно, иначе легко залить обратно 5.6.2;
- `Comport`/`BtAddress`/`BtAutomatic`/`BtPerformance` — в подключах устройства
  `...\SETEK - DiCE\DiCE-206751`.

## Настоящая причина `err=3` (найдена 22.09.2026 ~21:15 трассировкой DLL)

IAT-хук на `CreateFileW` (скрипт `scripts/dll_iat_trace.py`) показывает, что
`UsbHardware::Open()` открывает **единственный** путь, построенный из реестра:

```
\\?\usb#vid_17aa&pid_d1ce#<Name>@<BtAddress>#{4e8a43b0-...}\INTERFACE_0x00\PIPE_0x00
```

(`Name`/`BtAddress` читаются из `...\SETEK - DiCE\DiCE-206751`; там же читаются
`MF`, `VID`, `FW0..FW3`). Перебора через `SetupDi*` в этом пути нет — только
этот один `CreateFileW`.

При этом **USB-серийник устройства прошивка собирает сама**:
`%s-%06lu@%04lX%08lX` (@`0xFA1386`/`0xFA9EC2`) + шаблон
`DiCE-000000@000000000000` (@`0xFA00EE`/`0xFA129A`) → инстанс
`DiCE-<serial>@<BT-адрес, который знает прошивка>`.

Правило: **реестровый `BtAddress` обязан совпадать с тем, что прошивка
подставляет в USB-серийник**. Сейчас прошивка отдаёт `DiCE-206751@000000000000`
(патч CH05 убрал AT-хендшейк, из которого адрес попадал в переменную), а в
реестре `002113014D64` → путь не существует → `err=3` → DiagApp молча уходит на
BT, где и виден `RfcVersion` timeout.

Следствия:

- «лечение переустановкой драйвера» — скорее совпадение: драйвер тут не при чём,
  важно соответствие `BtAddress` ↔ USB-серийник (в 20:24 прошивка была заводская
  и отдавала `@002113014D64` — USB работал; после прошивки CH05-патча в 20:38
  стала `@000000000000` — USB перестал);
- быстрая проверка: выставить `BtAddress=000000000000` в подключе устройства
  (на подключ ACL не даёт писать без прав) → путь совпадёт, DiagApp откроется по
  USB; адрес для BT-сокета тогда останется только из поиска по имени;
- правильное решение: расширить CH05-патч так, чтобы прошивка подставляла в
  USB-серийник реальный адрес модуля (запись константы в ту же переменную, что
  заполнял AT-хендшейк), — тогда USB и BT снова согласованы.
