# Мост BT ↔ USB-хост: патч P1 (host TX → BT) и P2 (BT RX → host RX)

Патч-мост между «хост-каналом» (UART USB-моста, `ser_chan_usb`) и каналом
Bluetooth-модуля (`ser_chan_bt`). База — образ с уже применённым CH05-патчем
(`dice_5_6_3_ch05_full.mot`, вариант A+B+C1+C2+E+F + версия 5.6.3).

| Артефакт | Что это |
|---|---|
| `scripts/apply_bridge_patch.py` | генератор патча (S2-кодировщик переиспользован из `scripts/apply_ch05_patch.py`) |
| `dice_5_6_3_ch05_bridge.mot` | вход: `dice_5_6_3_ch05_full.mot` → выход: P1 + P2 (канал BT на **460800**) |
| `dice_5_6_3_ch05_bridge_115200.mot` | то же поверх `dice_5_6_3_ch05_full_115200.mot` (канал BT на **115200**; собирается как `python scripts\apply_bridge_patch.py --in dice_5_6_3_ch05_full_115200.mot --out dice_5_6_3_ch05_bridge_115200.mot`) |
| `--no-p1` / `--no-p2` | сборка только одной половины моста (для поэтапной проверки на железе) |
| `--verify-only` | только проверка входного файла, без записи |
| `docs/bridge_patch.md` | этот документ |

Порядок применения: `python scripts\apply_bridge_patch.py`
(по умолчанию `C:\misc\dice\dice_5_6_3_ch05_full.mot` →
`C:\misc\dice\dice_5_6_3_ch05_bridge.mot`).

> **Патч моста требует CH05-патча**: тела P1/P2 размещаются в «надгробии»
> функции F (`bt_baud_detect`, диапазон `0xFB0EC2..0xFB112B`), которое
> появляется только после CH05-патча (там 0xDE-заполнение). Генератор
> проверяет маркеры F (`EC 00` в `0xFB0EC2`, `FC` в `0xFB0EF5`) и то, что
> пещеры целиком залиты `0xDE`, и иначе отказывается работать.

## 1. Что установлено по IDB (перепроверка исходных допущений)

### 1.1 Индексы каналов: bt = 0, usb = 2, dbg = 3 (а НЕ 0/1)

`ser_chan_bt` (0x2425), `ser_chan_usb` (0x2426), `ser_chan_dbg` (0x2427) —
это **BSS-байты**, значения которых присваивает `serial_timer_register`
(0xFC0D9A): `09 92 FB 0C 08  MOV.B arg_4[FB],[arg_0[FB]]` — в переменную по
указателю пишется **номер режима** (mode), он же далее используется как индекс
структуры канала (`MULU.B #63h`) и как индекс таблицы баз UART-портов
(`MOV.L uart_port_base[A0], byte_26A0[A1]`, где `A0 = mode<<2`).

`serial_ports_boot_init` (0xFB6E20) вызывает его трижды:

| Блок | Вызов (адрес) | mode | переменная-приёмник | baud | буферы TX/RX | пины |
|---|---|---|---|---|---|---|
| BT | `0xFB6E4E` (`PUSH.B #0`, `PUSH.L #2425h`) | **0** | `ser_chan_bt = 0` | 460800 | 0x4000 / 0x2000 | P0.2 / P0.3 |
| USB | `0xFB6F1A` (`PUSH.B #2`, `PUSH.L #2426h`) | **2** | `ser_chan_usb = 2` | 115200 | 0x400 / 0x200 | P1.0 / P1.1 |
| dbg | `0xFB6FE8` (`PUSH.B #3`, `PUSH.L #2427h`) | **3** | `ser_chan_dbg = 3` | 115200 | 0x400 / 0x200 | P3.1 / P3.2 |

Косвенное подтверждение — таблица векторов (см. 1.2): обобщённые ISR
вызываются с константами 2 и 3.

Практический вывод: **сравнивать `R0L` с константой 1 нельзя**; патч читает
сами переменные (`MOV.B ser_chan_usb,R0L`). В документации `docs/uart_init.md`
роли каналов указаны как ch0/ch1/ch2 — фактические значения ch2 = USB, а не 1;
для `ser_chan_dbg` это ch3. (Ошибка была в переносе «режим → индекс канала».)

### 1.2 Кто и как обрабатывает приём/передачу

Векторная таблица (4-байтные LE-указатели) в `0xFAA180..0xFAA1FF`:

| Вектор | Обработчик | Канал | Что делает |
|---|---|---|---|
| `0xFAA1AC` | `sub_FC1E50` | **0 (BT)** | TX-empty ISR BT: дренирует TX-кольцо в `u0tb` (абсолютные адреса!) |
| `0xFAA1B0` | `sub_FC1E7E` | **0 (BT)** | RX ISR BT: читает `u0rb`, кладёт байт в RX-кольцо BT |
| `0xFAA1EC` | `sub_FB752A` | 2 (USB) | `MOV.B #2,R0L; JSR.A sub_FC1CA2` — kick TX |
| `0xFAA1F0` | `sub_FB7536` | 2 (USB) | `MOV.B #2,R0L; JSR.A chan_rx_isr` — RX |
| `0xFAA1F4` | `sub_FB7542` | 3 (dbg) | `MOV.B #3,R0L; JSR.A sub_FC1CA2` |
| `0xFAA1F8` | `sub_FB754E` | 3 (dbg) | `MOV.B #3,R0L; JSR.A chan_rx_isr` |

Каналы 0 (BT) и 2/3 (USB/dbg) имеют **разные** обработчики: BT — «ручные»
ISR с абсолютной адресацией полей канала 0, USB/dbg — обобщённые
`sub_FC1CA2`/`chan_rx_isr`, работающие с любым каналом через `chan*0x63`.

### 1.3 Исправление: `chan_rx_append` (0xFC1B92) — это НЕ приём, а ВЫГРУЗКА TX

Разбор 0xFC1B92..0xFC1CA1: функция берёт **следующий байт из TX-кольца**
(`dword_2673[chan]` + `word_2679[chan]`) и пишет его в регистр данных UART
(`[A1] = unk_2694[A0]`, ветка эха — `unk_2693[A0]`), т.е. это последняя стадия
**передачи**. Флаги, которые она читает:

* `unk_2699[chan]` — «есть байт к немедленной отправке»: если 1, байт берётся
  из `unk_2694[chan]` (не из кольца) и флаг сбрасывается;
* `unk_269A[chan]` — второй такой же путь через `unk_2693[chan]`;
* `unk_2696[chan]` — «передача запущена», `byte_268D` — «дренаж заказан».

Никакого отношения к RX-кольцу эта функция не имеет; RX-кольцо наполняется
**только** в ISR: `chan_rx_isr` (каналы 2/3, участок `0xFC1E0C..0xFC1E4F`) и
`sub_FC1E7E` (канал 0). Поэтому P2 сделан в RX-ISR BT, а не в `chan_rx_append`.

Кто зовёт `sub_FC154C` (единственный производитель TX-кольца — он один пишет
`ser_chan_table` = индекс записи TX, проверено по всему образу): j2534
SetConfiguration (FAB0AA), `bt_at_send`/`bt_at_tx` (BT, ch0),
`kline_iso9141_pump` ×3 и `iso15765`-пути через виртуальные каналы
(`MOV.B 2429h[A0],R0L` — физический канал из таблицы vchan; для хост-ссылки
это `ser_chan_usb`).

### 1.4 Раскладка структур каналов (база `0x2640`, шаг `0x63`)

| Поле | Адрес ch0 | Абсолютный адрес = имя + chan*0x63 | Смысл |
|---|---|---|---|
| `ser_chan_enabled` | 0x2641 | +0xC6 → 0x2707 (ch2) | 2 = UART инициализирован |
| `byte_2642` | 0x2642 | | mode (группа пинов) |

| `word_2679` | 0x2679 | 0x273F | индекс чтения TX (consumer) |
| `word_267D` | 0x267D | 0x2743 | маска TX |
| `dword_267F` | 0x267F | 0x2745 | буфер RX-кольца |

## 2. Патч P1 — host TX → BT TX

**Точка входа.** `sub_FC154C` @`0xFC154C`, первые 4 байта `EC 04 8F 7C`
(`ENTER #4; PUSHM R1,R2,R3,A0,A1`) заменяются на `JMP.A 0xFB0F00`.
Внешних переходов внутрь пролога нет (`xrefs` на 0xFC154D/E/F: 0/1/0, причём
единственный — fallthrough из самого `ENTER`, который мы и заменяем).

**Cave1** @`0xFB0F00` (41 байт кода + 0xDE до 0xFB0F40):

| Смещ. | Байты | Инструкция | Донор |
|---|---|---|---|
| +00 | `EC 04` | `ENTER #4` | 0xFC154C |
| +02 | `8F 7C` | `PUSHM R1,R2,R3,A0,A1` | 0xFC154E |
| +04 | `4E` | `MOV.B R0L,R1L` — сохранить chan | 0xFB1632 |
| +05 | `18 26 24` | `MOV.B ser_chan_usb,R0L` | 0xFAB806 |
| +08 | `C8 B6` | `CMP.B R1L,R0L` | 0xFB1636 |
| +0A | `9A 1A` | `JNE/NZ` на +0x25 (конец зеркала) | 0xFB1653 (смещение пересчитано) |
| +0C | `C8 BB` | `MOV.B R1L,R0L` | 0xFC1BBB |
| +0E | `09 39 08` | `MOV.W [arg_0[FB]],R0` — **локальная** копия длины | 0xFB8507 |
| +11 | `31 FC` | `MOV.W R0,var_4[FB]` | 0xFA2DCF |
| +13 | `A2 C1 0C` | `PUSH.L arg_4[FB]` (data ptr) | 0xFB1642 |
| +16 | `D3 DA FC` | `MOVA var_4[FB],A0` (&лок. длины) | 0xFB0DFA |
| +19 | `A0 81` | `PUSH.L A0` | 0xFB0DFD |
| +1B | `18 25 24` | `MOV.B ser_chan_bt,R0L` | 0xFB0E16 |
| +1E | `CD 4C 15 FC` | `JSR.A sub_FC154C` (chan = BT) | 0xFB0E02 |
| +22 | `73` | `ADD.L #8,SP` | 0xFB0E06 |
| +23 | `C8 BB` | `MOV.B R1L,R0L` — вернуть исходный chan | 0xFC1BBB |
| +25 | `CC 50 15 FC` | `JMP.A 0xFC1550` (`MOV.W #0,R1` — тело оригинала) | 0xFA0000 (опкод) |

Семантика: если `chan == ser_chan_usb`, то до основной работы выполняется
второй вызов `sub_FC154C` с `chan = ser_chan_bt` и **той же** длиной из
локальной копии (`var_4[FB]` кадра — в исходном теле это поле перезаписывается
перед чтением, поэтому переиспользование безопасно). Счётчик вызывающего
(`*arg_0`) не портится: рекурсивный вызов пишет в локальную копию, а не в
`arg_0`. Затем управление возвращается в исходное тело с восстановленным
`R0L`. Рекурсия не бесконечна: у вложенного вызова `chan = BT ≠ USB`, он
сразу уходит на `0xFC1550`.

Прерывания: `sub_FC154C` вызывается только из основного цикла (ни один ISR его
не зовёт), поэтому дополнительной защиты не требуется; конкурентного
производителя у одного кольца нет.

## 3. Патч P2 — BT RX → RX-кольцо host-канала

**Точка входа.** `sub_FC1E7E` (RX ISR BT) @`0xFC1ED7`, инструкция
`C7 CB 83 26` (`MOV.W R2,word_2683` — фиксация нового индекса записи RX
канала 0 после сохранения байта) заменяется на `JSR.A 0xFB0F40`.

**Cave2** @`0xFB0F40` (18 байт кода + 0xDE):

| Смещ. | Байты | Инструкция | Донор |
|---|---|---|---|
| +00 | `D3 EE` | `FCLR I` — атомарность обновления RX-кольца host-канала | 0xFA3515 |
| +02 | `C7 CB 83 26` | `MOV.W R2,word_2683` (вытесненная инструкция) | 0xFC1ED7 |
| +06 | `EC 04` | `ENTER #4` | 0xFC154C |
| +08 | `8F 7C` | `PUSHM R1,R2,R3,A0,A1` | 0xFC154E |
| +0A | `4E` | `MOV.B R0L,R1L` — байт в R1L | 0xFB1632 |
| +0B | `18 26 24` | `MOV.B ser_chan_usb,R0L` — канал = USB | 0xFAB806 |
| +0E | `CC 0C 1E FC` | `JMP.A 0xFC1E0C` — вход в обобщённый блок RX | 0xFA0000 (опкод) |

Блок `0xFC1E0C..0xFC1E4F` внутри `chan_rx_isr` — «чистое» добавление байта в
RX-кольцо канала, параметризованное `R0L` (канал) и `R1L` (байт):
пересчёт `chan*0x63` → `word_2683`, `+1`, `& word_2689`, сравнение с
`word_2685` (кольцо полно → `OR.W #80h,word_2690` и выход), иначе запись в
`dword_267F[chan] + idx` и `word_2683[chan] = idx`. Блок заканчивается
`POPM R1,R2,R3,A0,A1; EXITD`, поэтому он возвращает управление **прямо в RX
ISR BT** (кадр `ENTER #4`+`PUSHM` создан нашей пещерой ровно такой же, как в
`chan_rx_isr`), после чего ISR выполняет свои `POPM R0,R1,R2,R3,A0` и `REIT`.
Использование готового блока гарантирует идентичную семантику кольца, включая
маску, индекс и флаг переполнения.

`FCLR I` закрывает окно read-modify-write индекса RX host-канала: RX-ISR
хост-канала (`chan_rx_isr`, chan = 2) выполняется по тому же коду и мог бы
вклиниться между чтением и записью `word_2683[usb]`. Флаг `I` не нужно
восстанавливать вручную: `REIT` восстанавливает регистр флагов из стека
(`~30` инструкций с запрещёнными прерываниями ≈ 3 мкс при 30 МГц — при
115200/460800 это доли байтового интервала).

**Чего P2 НЕ делает:** ничего не отправляет в USB-TX; байт попадает в
RX-кольцо host-канала, откуда его читает хостовый слой (vchan/протокол,
`sub_FC15F2`), т.е. PC видит по USB то, что пришло из BT. Флаг эха `unk_2699`
здесь ни при чём (он относится к выгрузке TX, см. 1.3) — специально
проверено.

## 4. Верификация

1. **Донорство кодировок.** Генератор проверяет, что 16 инструкций из 21
   байт-в-байт совпадают со своими донорами в исходном образе, а 5 (три
   `JMP.A`/`JSR.A` с новыми адресами и `JNE` с пересчитанным смещением)
   используют донорский опкод. Правило коротких переходов M32C
   (`target = addr + 1 + rel8`) проверено по всем 3789 коротким переходам
   образа — расхождений 0.
2. **Независимый дизассемблер.** Байты, реально записанные в
   `dice_5_6_3_ch05_bridge.mot`, декодированы процессорным модулем M32C в IDA
   (во временной области, затем область восстановлена): все инструкции
   распознаны так, как задумано, `JNE` попадает ровно на `JMP.A`, абсолютные
   адреса `JMP.A/JSR.A` — `0xFC1550`, `0xFC1E0C`, `0xFB0F00`, `0xFB0F40`.
3. **S2.** 10186 записей S2 + S0/S8 как в исходнике; все чексуммы
   пересчитаны и повторно проверены (0 ошибок), все патченные байты
   перечитаны из выходного файла.
4. **Полная сверка образа** через `scripts/srec2bin.py` (импортируется как
   модуль): отличие от `dice_5_6_3_ch05_full.mot` — ровно 67 байт в четырёх
   диапазонах `FB0F00..FB0F28`, `FB0F40..FB0F51`, `FC154C..FC154F`,
   `FC1ED7..FC1EDA`; вне патченных диапазонов изменений нет.
5. Побочные артефакты в IDB отсутствуют: временная область `0xFD2400`
   (вне образа, после `0xFD1FF0`) восстановлена побайтово и снята с учёта
   (флаги `0x0`, как у соседних неиспользуемых адресов).

## 5. Риски и ограничения

1. **RFC-транспорт лежит в отсутствующем банке.** Байтовый I/O RFC-потока
   идёт через `rfc_tx_byte` (0xFA2F5C → `JSR.A unk_FFA24E`) и
   `rfc_rx_byte` (0xFA2F70 → `JSR.A unk_FFA2F2`), т.е. в банк
   `0xFFAxxx`, которого нет ни в `.mot` (образ кончается на `0xFD1FF0`), ни
   в IDB. **Если boot-банк пишет регистр host-UART напрямую**, ответ сервиса
   версии (RFC) НЕ попадёт в BT: P1 зеркалирует только путь через
   `sub_FC154C`. Если boot-банк пользуется канальным слоем приложения
   (вызывает `sub_FC154C`/`chan_rx_append` кросс-банково) — попадёт.
   Проверяется либо чтением boot-банка (`docs/rfc_bootloader_read.md`), либо
   опытом на железе (см. §6). Обходной вариант, если опыт покажет «не
   попадает»: перенести P1 на точку физической выдачи байта host-канала
   (`chan_rx_append` при `chan == ser_chan_usb`) — это покроет всё, что
   проходит через TX-кольцо host-канала, в том числе вызовы из boot-банка,
   но не покроет прямую запись в `u0tb` из boot-банка (её вообще ничем в
   приложении не перехватить).
2. **RX-кольцо host-канала маленькое (0x200 = 512 байт).** Если USB-хост не
   вычитывает кольцо, BT-трафик его заполнит; при этом (а) в
   `word_2690[usb]` встанет бит 7 «переполнение RX», (б) пока кольцо полно,
   блок отбрасывает и «зеркальные», и **собственные** host-байты. Пока по USB
   идёт сессия, host-стек кольцо дренирует; при работе «только по BT» кольцо
   останется полным и бит переполнения будет стоять — это ожидаемое
   поведение, но его стоит учитывать при диагностике. При необходимости
   порог можно ужесточить (зеркалировать только при большом запасе места).
3. **Кольцо BT (0x2000) и его TX (0x4000)** большие, но если BT-модуль не
   вычитывает линию, зеркальные байты будут отбрасываться с кодом 9/частичной
   записью — это штатное поведение `sub_FC154C`.
4. **Один и тот же байт приходит в оба канала независимо**: P2 не «перекидывает»
   приём, а дублирует; штатная ветка BT-ISR (эхо-фильтр по `unk_2694` на
   0xFC1DA3, разбор ошибок линии) для BT-канала не менялась.
5. **Железом не проверялось** (по условию задачи — устройством занимается
   человек). Ничего не прошивалось, `FwdlApp.exe`/`DiagApp.exe` не
   запускались, банк `0xFF9xxx` не трогался.
6. **Зависимость от CH05-патча** (см. врезку в начале) — иного свободного
   места в образе нет: пещеры взяты из «надгробия» функции F.

## 6. Что проверить на железе (план)

1. Прошить `dice_5_6_3_ch05_bridge.mot`.
2. **P1**: подключиться по BT (SPP «J2534») и запросить версию/открыть
   J2534-сессию так, чтобы ответ шёл в USB-канал → в BT-терминале должен
   появиться тот же поток байт. Если нет — проверить гипотезу §5.1:
   собрать `--no-p2` и посмотреть, идёт ли трафик вообще; затем (при
   необходимости) прочитать boot-банк.
3. **P2**: отправить байты в BT (SPP) → они должны появиться в RX-кольце
   host-канала (`word_2683[usb]`, буфер `dword_267F[usb]`; при живом хосте —
   как входящие J2534-сообщения/USB-трафик). Диагностический вариант —
   `--no-p1`, чтобы исключить взаимное влияние.
4. Контроль регистров (для отладки через debug-UART): `0x2749` (RX write idx
   USB), `0x274B` (RX read idx USB), `0x2756` (статус USB, бит 7 = overflow),
   `0x273D/0x273F` (TX write/read idx USB), `0x2739` (указатель TX-кольца USB).

## 7. Что осталось доуточнить

* Прочитанного в образе достаточно для обоих патчей; **не хватает только
  банка bootloader'а** (`0xFF9xxx`/`0xFFAxxx`), чтобы утверждать, что
  RFC-ответ физически уходит через канальный слой приложения (§5.1).
  Это единственный открытый вопрос, влияющий на достижение цели «ответ
  сервиса версии уходит и в BT».
* Значения `ser_chan_*` получены статически из `serial_timer_register`
  (`*arg_0 = mode`) и порядка вызовов в `serial_ports_boot_init`; при первом
  же подключении стоит подтвердить их чтением RAM (0x2425/0x2426/0x2427)
  через debug-канал.
