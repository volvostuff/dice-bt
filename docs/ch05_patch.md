# Патч прошивки под CH05 (предзапрограммированный BT-модуль)

Цель: убрать из `dice_5_6_2.mot` **все** AT-зависимости, чтобы адаптер работал с
преднастроенным CH05 (SPP-сервер «J2534», коннект со стороны Windows уже
работает, AT-совместимости у модуля нет). Фазы инициализации блютуз
(сканирование baud, ATZ, AT-конфиг, исходящий dial) полностью исключаются.
Патч чистый, байтовый, по S-записям; исходный файл не тронут.

## Артефакты

| Файл | Патчи | Когда |
|---|---|---|
| `dice_5_6_2_ch05.mot` | **A + B + E + F** (обязательный набор) | P2.1 = RESET (или не используется) |
| `dice_5_6_2_ch05_full.mot` | **A + B + C1 + C2 + E + F** | P2.1 = EN (питание модуля) |
| `scripts/apply_ch05_patch.py` | генератор | `--with-reset-off` (C1+C2), `--verify-only` |
| `scripts/srec2bin.py` | S-record → бинарный образ | утилита/сверка |

## Почему нужно 4 патча (а не 2)

При детальном разборе выяснилось, что данных с BT в оригинале нельзя получить
без AT-фазы:

1. **Гейт приёма/отдачи**: `bt_rx_read` (0xFB1676), `bt_at_tx` (0xFB162E) и
   `sub_FB16C8` (0xFB16CF) проверяют `ser_boot_state == 1`
   (`CMP.B ser_boot_state, R0L` при `R0L = 1`), иначе молча возвращают
   «нет данных».
2. **Кто пишет `ser_boot_state` (0x23C9)** — полный список (XrefsTo, сверено
   с образом):
   - `bt_baud_detect`: fb0f3a (`=5`, быстрый путь), fb0f4e (`=4`, mode 9),
     fb1124 (`=0`, сбой);
   - `sub_FB16A8` (0xFB16A8): при значении 0/1 **читает в flag вх. P5.4**
     (индикатор «модуль подключён», настроен как input: `BCLR #4,p5` +
     `BCLR #4,pd5` в инициализации порта fb7c79). Это **единственный**
     рантайм-путь в 1.

   Т.е. значение 1 достигается **только** через P5.4. Если CH05 «подключён»
   иначе (или линия не подведена) — весь BT-RX/TX заблокирован.

   → нужен патч **E** (форс `ser_boot_state = 1` в самом `sub_FB16A8`).

3. **Baud**: `bt_baud_detect` при молчании модуля (CH05 на AT не отвечает)
   проходит 8-шаговый скан 9600…921600 (~28 с), после которого линия
   остаётся на **последней скорости таблицы (921600)** — не на 460800.
   → нужен патч **F** (замена всей функции на безусловную инициализацию
   на 460800).

4. **Dial**: каждый J2534 Open шлёт `ATD<адрес>,1101` (исходящий вызов,
   `sub_FB15BE`, вызовы 0xFAB889 в `sub_FAB86C` и 0xFBF192 в `sub_FBF18A`);
   если нет `OK` — Open падает. CH05 — SPP-сервер (дозванивается Windows),
   MCU дозваниваться не должен. → патч **B**.

## Патчи (адреса в образе; офсет в .bin = адрес − 0xFA0000)

| # | Адрес (диапазон) | Было | Стало | Назначение |
|---|---|---|---|---|
| **F** | `0xFB0EC2..0xFB112B` (618 B, вся `bt_baud_detect`) | AT-скан + ATZ + ATS521-проба + AT-конфиг, 28 c при молчании, baud остаётся 921600 | `ENTER #0; MOV.L #460800,ser_cur_baud+2; serial_channel_reset; serial_channel_set_config(460800,0); uart_port_init; serial_channel_start; ser_boot_state=1; return 0` (52 B + NOP-заполнение) | **обязателен.** Убирает всю фазу инициализации BT; линии сразу 460800, flag=1. Все команды скопированы 1:1 из оригинала (donor-байты). Единственный вызывающий, проверяющий R0 (`sub_FC0996`, fc0a43), тут же перетирает результат `rfc_media_init` |
| **E** | `0xFB16A8..0xFB16BC` (21 B, `sub_FB16A8`) | `state 0/1 → state := P5.4; 4/5 sticky` | `MOV.B #1,R0L; MOV.B R0L,ser_boot_state; RTS` + NOP | **обязателен.** Линк-статус всегда «подключён» независимо от P5.4; открывает RX/TX-гейт. Внешних xrefs внутрь хвоста функции нет (входы только в начало, fb16a8 — кода не ломает, тело заменено целиком) |
| **B** | `0xFB15BE..0xFB161F` (98 B, `sub_FB15BE`) | `ATD%s,1101` + ожидание OK | `MOV.B #0,R0L; RTS` + NOP | **обязателен.** Open больше не падает из-за dial; xrefs в хвост (fb15c5..fb161f) отсутствуют — замена безопасна |
| **A** | `0xFB13C6` (3 B, в `bt_line_probe`) | `CF 65 FD` (JSR.W bt_at_init) | `DE DE DE` | страховка: factory-AT-конфиг (13 команд) уже не вызывается с F (остался только путь через `sub_FB1620` при Open); NOP гарантирует, что ничего не уйдёт в CH05 |
| **C1** | `0xFB12CB` (4 B, в `bt_line_probe`) | `D6 F9 C4 03` (BSET #1,p2) | `DE DE DE DE` | **опционален.** импульс 200 мс на P2.1 при Open |
| **C2** | `0xFB12DB` (4 B) | `D6 F1 C4 03` (BCLR #1,p2) | `DE DE DE DE` | вторая половина импульса |

C1/C2: если P2.1 → RESET модуля — оставить как есть (импульс при каждом
Open допустим); если P2.1 → EN (питание) — снять, иначе каждый Open
на мгновение выключит питание CH05.

## Что теперь происходит по времени

1. **Старт MCU**: `rfc_media_init` → `bt_baud_detect` (заменён, F):
   канал 0 сразу 460800, 8N1, UART начат, `ser_boot_state=1`. **Ноль AT,
   ноль ожидания** (было до 28 с).
2. **J2534 Open**: `sub_FAB86C` → dial `sub_FB15BE` (заменён, B)
   возвращает 0 сразу → канал стартует, `bt_at_tx`/`bt_rx_read`
   пропускаются гейтом (state уже 1).
3. **Данные**: `bt_rx_read`/`bt_at_tx`/`sub_FB16C8` работают в обычном
   режиме; `sub_FB16A8` (E) всегда возвращает 1, `byte_23D6` (связь)
   ведёт себя штатно.
4. P2.1-импульс — только по C1/C2, если их снять.

## Верификация

- S2-парсер: round-trip 10186/10186 записей (rebuild == original line);
  учтён специфичный формат файла: байт-счётчик **включает чексумму**,
  чексумма = `(0xFF − (count+addr+data)) & 0xFF`.
- Чексуммы всех S2 в обоих выходных файлах валидны (0 bad, self-check).
- Независимая сверка `srec2bin.py`: декодированные образы обоих .mot
  отличаются от оригинала **только** в ожидаемых диапазонах:
  - `dice_5_6_2_ch05.mot`: 736 байт = F (618) + B (98) + E (21) + A (3) +
    24 B хвост `bt_baud_detect`, где кончался код, но не закончилась запись;
  - `dice_5_6_2_ch05_full.mot`: +C1 (4) +C2 (4) = 744 байта.
- Внесённые байты: все инструкции скопированы как доноры из оригинального
  кода (см. таблицу), никаких выдуманных энкодингов; `NOP=DE`, `RTS=DF`,
  `EXITD=FC`, `JSR.A=CD xx xx xx`.

## Побочный эффект патча: USB-серийник теряет BT-адрес (найдено 22.09.2026)

Прошивка собирает строку USB-серийника как `DiCE-<serial>@<BT-адрес>`:
формат `%s-%06lu@%04lX%08lX` (@`0xFA1386`/`0xFA9EC2`) + шаблон
`DiCE-000000@000000000000` (@`0xFA00EE`/`0xFA129A`), т.е. инстанс устройства
получается `DiCE-206751@<адрес>`. Адрес в эту переменную попадал из
AT-хендшейка, который снимают патчи **F** (и **A**) → теперь устройство
enum-ится как `DiCE-206751@000000000000`.

Хост при этом (`TSDiCE64.dll`, проверено трассировкой
`scripts/dll_iat_trace.py`) строит путь USB-устройства как
`\\?\usb#vid_17aa&pid_d1ce#<Name>@<BtAddress>#{4e8a43b0-...}\INTERFACE_0x00\PIPE_0x00`
из реестра, т.е. ждёт `DiCE-206751@<BtAddress>`. Несовпадение →
`UsbHardware::Open()` → `err=3` → DiagApp молча уходит на BT.

Лечение: либо `BtAddress=000000000000` (тогда USB работает, но адрес для
BT-сокета остаётся только из поиска по имени), либо доработка патча —
подставлять в USB-серийник реальный адрес модуля (запись константы туда же,
куда писал AT-хендшейк).

## Порядок проверки на железе

1. Прошить `dice_5_6_2_ch05.mot` (или `_full`, если P2.1 = EN).
2. С Windows: убедиться, что CH05 сопряжён/подключён (SPP) как раньше.
3. Открыть J2534-порт в приложении:
   - Open должен проходить **мгновенно** (ни 28-секундного скана, ни dial
     не должно быть).
   - Если Open проходит, но данных нет — смотрите, что делает P2.1:
     при EN и отсутствии C1/C2 модуль мог быть сброшен питанием;
     перешить на `_full`.
4. Контрольный тест AT-независимости: отключить/не сопрягать модуль
   → адаптер всё равно стартует за секунды и Open проходит; данные
   появятся, когда модуль подключится со стороны Windows.

## Бамп версии (5.6.2 → 5.6.3)

Версия хранится в заголовке образа (адрес = 0xFA0000 + офсет):

| Адрес | Байт | Назначение |
|---|---|---|
| `0xFA0004` | major | 5 |
| `0xFA0005` | minor | 6 |
| `0xFA0006..07` | 0xFF 0xFF | зарезервировано (читаются как слово) |
| `0xFA0008` | build | 2 → **3** |

Код (`0xFA27F2..0xFA284D`) только читает/сравнивает эти байты,
контрольной суммы над ними нет → меняется ровно один байт.
Генератор: `scripts/bump_version.py` (`--version M.m.b`, переиспользует
S2-кодировщик). Вывод — поверх CH05-базы:

| Файл | Состав |
|---|---|
| `dice_5_6_3_ch05.mot` | CH05 (A+B+E+F) + версия 5.6.3 |
| `dice_5_6_3_ch05_full.mot` | CH05 (A+B+C1+C2+E+F) + версия 5.6.3 |

Сверка: против соответствующей CH05-базы разница = ровно 1 байт
(`0xFA0008: 02→03`), чексуммы S2 валидны.

## Контрольная сумма: есть ли проверка целостности?

- **Внутри `.mot` хранящейся контрольной суммы нет** (S0/S8 — только base
  address; в начале/конце образа magic/sum отсутствуют). Байтовый патч сам
  по себе ничего не «ломает» на уровне файла.
- **Самопроверки собственного кода на старте MCU в образе приложения нет**
  (таблицы CRC32/CRC16 в образе не найдено, циклов суммирования по флешу
  нет).
- **Протокольная проверка есть**: RFC-кадры Windows-лоадера
  (`RfcFWDL32.dll`) несут header-checksum (`len + 0x1E`) и
  message-checksum (сумма FID+payload `+ 0x69`); ошибки отвечаются как
  `ERR_RFC_HCS`/`ERR_RFC_MCS`. Это проверка канала, а не образа.
- **Проверка содержимого флеш после прошивки есть**: экспорты
  `RfcFWDL32.dll` `FwdlCS/FwdlErase/FwdlProg/FwdlRead/FwdlLock` шлют
  MCU-команды (FID `0x7D/0x77/0x78/0x79/0x7A`); ответ на `FwdlCS(addr)` —
  16-битная сумма диапазона, которую хост сверяет. **Обработчики этих
  команд живут в bootloader-банке 0xFF9xxx (другая флеш-банка), которого
  нет в `dice_5_6_2.mot`** (образ — только `0xFA0000..0xFD1FF0`);
  диспетчер команд в приложении — `0xFA2AE2` (таблица указателей `dword_6C8`).
  Задача чтения bootloader'а через `RfcFWDL32.dll` — отдельный документ
  [rfc_bootloader_read.md](rfc_bootloader_read.md) (на паузе).
- **Практический вывод для нашего патча**: утилита прошивки считает сумму
  от **того .mot, который ей дали**, т.е. патченный файл сверится сам с
  собой и прошивка пройдёт. Рисков нет; сверки «от оригинала» хосту негде
  взять.

## Контрольные точки в IDB (для сверки)

- `bt_baud_detect` 0xFB0EC2 — тело заменено (F); prologue `ENTER #0`
  сохранён, `PUSHM R1,R2,R3,A0,A1` больше не нужен (функция не вложена).
- `sub_FB16A8` 0xFB16A8 — форс `ser_boot_state=1` (E).
- `bt_rx_read` 0xFB1670 / `bt_at_tx` 0xFB162E / `sub_FB16C8` 0xFB16C8 —
  гейты, не тронуты; после E проходят всегда.
- `sub_FB15BE` 0xFB15BE — «успешный dial» (B).
- P5.4 (вх.) больше ни на что не влияет (E читает его не будет).
