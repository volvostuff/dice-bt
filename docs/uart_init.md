# UART — скорости инициализации и роли каналов (dice_5_6_2.mot, Renesas M32C/85)

Анализ через IDA MCP (idb: `dice_5_6_2.mot.i64`, сохранён с именами/комментариями).
Код — 32-битный M32C (`ENTER/EXITD`, JSR.W/JSR.A). Карта SFR — по `m32c80.cfg`:
UART0 `u0smr4`=0x364, `u0mr`=0x368, `u0brg`=0x369, `u0c0`=0x36C, `u0c1`=0x36D, `u0rb`=0x36E.
В IDB SFR2 = `0x400000 + SFR×0x10000` (см. 0x40369 = u0brg).

## Роли каналов: USB / Bluetooth / debug UART

MCU **M32C/85 не имеет собственного USB-контроллера** (в `m32c80.cfg` нет USB-регистров,
в прошивке нет USB-descriptor/endpoint-кода). Поэтому USB — это **внешний мост
USB-UART** на плате; со стороны хоста он виден как COM-порт (`Comport=COM12`
в `dice.reg`). Все три последовательных канала — «обычные» UART-модули M32C/85,
мультиплексируемые через базу `uart_port_base`.

| Канал | Имя в IDB (BSS) | Пины | SFR-режим* | Boot-baud | Роль |
|---|---|---|---|---|---|
| Канал (значение `ser_chan_*`) | Имя в IDB (BSS) | Пины | SFR-режим* | Boot-baud | Роль |
|---|---|---|---|---|---|
| 0 | `ser_chan_bt` (0x2425) | P0.2 (TX)/P0.3 (RX) | mode 0 | 460800 | **Bluetooth** (SPP, профиль «J2534») |
| 2 | `ser_chan_usb` (0x2426) | P1.0 (TX)/P1.1 (RX) | mode 2 | 115200 | **USB** (хост-ссылка J2534, мост USB-UART → COM12) |
| 3 | `ser_chan_dbg` (0x2427) | P3.1 (TX)/P3.2 (RX) | mode 3 | 115200 | **Debug/trace UART** (сервисный/отладочный вывод) |

> **Уточнение 22.09.2026 (проверено по IDB):** индексы каналов — `bt=0`,
> `usb=2`, `dbg=3` (индекс 1 не используется). Доказательство:
> `serial_ports_boot_init` (0xFB6E20) зовёт `serial_timer_register` с
> `PUSH.B #0/#2/#3` и `PUSH.L #2425h/#2426h/#2427h`, а тот делает
> `*arg_0 = mode`; подтверждают векторы 0xFAA1EC/F0 (`MOV.B #2,R0L;
> chan_rx_isr`) и 0xFAA1F4/F8 (`MOV.B #3,R0L`). В патчах канал надёжнее
> сравнивать с самой переменной (`ser_chan_usb`), а не с константой.

\* «Режим» — поле `byte_2642[A0]` структуры канала (стр. 0x2640, шаг 0x63),
пишется `serial_timer_register` при boot: bt←mode 0, usb←mode 2, dbg←mode 3
(0xfb6e5c/0xfb6f2a/0xfb6fec); по нему `serial_pin_config` (0xfc1770)
выбирает группу пинов.

### Примитивы канального I/O (проверено 22.09.2026 по IDB)

| Функция | Что делает |
|---|---|
| `sub_FC154C(chan, &len, data)` | **единственный продюсер TX-кольца**: кладёт байты в кольцо канала (индекс записи `ser_chan_table` в образе пишет только он). Вызов из `bt_at_send` @0xFB0DF7..0xFB0E06 |
| `sub_FC15F2(chan, &len, buf)` | выборка байтов из RX-кольца канала (её же использует `bt_rx_read` @0xFB1670) |
| `chan_rx_append` (0xFC1B92) | **выгрузка TX**, а не приём: берёт байт из TX-кольца (`dword_2673` + `word_2679`) и пишет в регистр данных UART; `unk_2699[chan]` = «есть байт к немедленной отправке». Имя в IDB обманчиво |
| `chan_rx_isr` (0xFC1E0C..0xFC1E4F) | общий блок наполнения RX-кольца для каналов 2/3 |
| `sub_FC1E7E` | наполнение RX-кольца канала 0 (BT), абсолютная адресация |

Векторы: 0xFAA1B0 → `sub_FC1E7E` (RX BT), 0xFAA1AC → `sub_FC1E50`
(TX-empty BT), 0xFAA1EC/F0 → `chan_rx_isr` (канал 2), 0xFAA1F4/F8 → канал 3.

Размеры колец: BT TX 0x4000 / RX 0x2000; USB (ch2) TX 0x400 / RX 0x200.
Адреса ch2: RX-wr `0x2749`, RX-rd `0x274B`, RX-buf `0x2745`, статус `0x2756`,
TX-wr `0x273D`. Разбор и практическое применение (мост BT↔USB) —
[bridge_patch.md](bridge_patch.md).

### Доказательства

**ch0 = Bluetooth:**
- Инициализация BT-чипа идёт **по тем же RX/TX линиям (P0.2/P0.3)**, что и
  передача данных: AT-хендшейк `ATZ`/`!<BISM>!`/`AT` и вся последовательность
  `bt_at_init` отправляются через `bt_at_send` → `sub_FC148E` (общий TX драйвер)
  с хардкодом `ser_chan_bt`; приём — общий RX (буфер канала, `bt_rx_read`).
  Отдельных управляющих линий нет — единственный GPIO: импульс **P2.1**
  (200 мс) перед хендшейком (`bt_line_probe`, 0xfb12cb) — reset/enable BT-чипа.
- **Двусторонняя настройка UART-линии**: AT-команды настраивают UART *модуля*
  (`ATS521=%lu` — baud), а UART *MCU* настраивается независимо записью SFR
  (`serial_channel_set_config` + `uart_port_init`). `bt_boot_atz_probe` (0xfb1508)
  делает это атомарно: `AT`→OK → `ATS521=N` → re-init нашей UART на N → `AT`→OK.
  Автодетект (`bt_baud_detect`, 9600…921600) нужен, т.к. MCU не «помнит» baud
  после reset, а модуль — сохраняет. Остальные команды (`AT+BTS/AT+BTK/AT+BTF`,
  `ATS512`) — не UART, а радионастройка SPP, сохраняется в flash модуля (`AT+BTP`).
- **Сценарий режимов**: после reset чип SPP-модуля по умолчанию в *командном*
  режиме — UART принимает AT-команды. `bt_at_init` конфигурирует его как SPP-сервер
  (`ATS512=4`, `AT+BTS="J2534"`, `AT+BTK="1234"` …), а финальная `AT+BTP`
  сохраняет конфиг в flash и **перезагружает модуль**: UART становится
  *прозрачным каналом данных* (SPP-поток J2534), AT-режим становится недоступен.
  Единственная активная AT-команда `ATD%s,1101` (исходящий dial) — только до
  установки соединения.
- AT-инициализация BT-чипа: `bt_at_init` (0xfb112c), точный порядок:
  `ATE0` (эхо off) → `ATS512=4` (SPP-порты) → `ATS515=$300`, `ATS533=0`,
  `ATS534=0`, `ATS538=1` (опции) → **`AT+BTK="1234"` (PIN)** →
  **`AT+BTS="J2534"` (имя SPP-профиля)** → `ATS507=2`, `ATS0=-1` →
  **`AT+BTP` (сохранить в flash + reboot)** → `AT&W` (reset UART-параметров).
  ★-команды — настройка именно BT-модуля (радио/SPP), видимая хостом:
  сервис «J2534», PIN 1234. Имя устройства `AT+BTF="DiCE"`/`AT+BTN="DiCE"`
  (запрос `AT+BTN?`) — в других подсистемах (таблицы 0xfb4b0a/fb71be/fbca62/fbe06e),
  задаётся динамически (как `DiCE-206751` в реестре).
- Транслятор `bt_at_send` (0xfb0dda) **хардкодит** `ser_chan_bt` перед отправкой
  (0xfb0de4/0xfb0dff/…); boot-зонд `bt_boot_atz_probe` (0xfb1508) тоже только ch0.
- Автодетект скорости `bt_baud_detect` (0xfb0ec2) работает только с ch0
  (460800 → фоллбек 9600).
- `dice.reg`: `BtAddress=002113014D64`, `BtPerformance=1` — отдельный BT-интерфейс.

**ch1 = USB (хост-ссылка J2534):**
- `usb_host_link_init` (0xfbde56) создаёт **два виртуальных канала (vchan)**
  на `ser_chan_usb` через `host_vchan_create` (0xfba29c, таблица шаг 0x1CF,
  база 0x2429) и запускает подсистемы (0xfbde40/0xfbde4b, 0xfbe5f0).
- Все драйверы протоколов (ISO15765, ISO9141/K-line) работают через виртуальные
  каналы этой таблицы, т.е. поверх USB-ссылки.
- `j2534_SetConfiguration_uart` (0xfab042, вызов из 0xfab7ee) при смене baud
  хостом меняет скорость **одновременно** `ser_chan_usb` + `ser_chan_dbg` —
  хост-пара «USB + debug» ведёт себя как один логический интерфейс.

**ch2 = debug UART:**
- Второй член пары в `j2534_SetConfiguration_uart` (0xfab801): debug-порт
  всегда синхронизирован со скоростью хост-порта.
- Отладочные дампы (`%s Baud %9lu`, CAN-статистика, регистры Cx*) и баннер
  `serial_identity_print` (0xfbda80) идут на хост-пару, а не на BT-канал.
- Строка `usbbutton` (0xfa9a53) — триггер RFC-подсистемы прошивки/медиа
  `rfc_media_init` (0xfc1ee8, файлы `config.cfg`, `_000.log`) — это хост-команда
  управления адаптером (загрузка прошивки по USB), не BT.

> Примечание: точный физический номер UART-модуля (UART0..4) по каждому каналу
> из бинария не вычислить — `uart_port_base` устанавливается рантаймом/boot-кодом,
> отсутствующим в .mot. Определены только группы пинов (P0/P1/P3) и роли.

## Ответ: скорости при инициализации

### 1. Boot-инициализация — `serial_ports_boot_init` (0xfb6dbe–0xfb70a6)

Три последовательных канала (структура: база RAM 0x2640, шаг 0x63=99 байт,
`+1` = флаг «включён», `+3` = baud) инициализируются:

| Канал (BSS) | Скорость | Адрес |
|---|---|---|
| `ser_chan_bt` (0x2425) | **460800** | 0xfb6e68 `PUSH.L #70800h` |
| `ser_chan_usb` (0x2426) | **115200** | 0xfb6f36 `PUSH.L #1C200h` |
| `ser_chan_dbg` (0x2427) | **115200** | 0xfb6ff8 `PUSH.L #1C200h` |

Порядок на канал: `serial_timer_register` → `serial_channel_set_config`
(idx0=baud, idx1=stop, idx2=данные=8, idx3=parity, idx4/7=0, idx5/6=6/3)
→ **`uart_port_init`** — реальная инициализация UART-железа.

### 2. Скоростной скан / автодетект — `bt_baud_detect` (0xfb0ec2–0xfb112b)

Вызывается с 0xfb72e6 и 0xfc0a43 (только ch0/BT). Строит таблицу стандартных
скоростей (0xfb0ec6–0xfb0f00) и циклом i=0..7 ставит каналу baud[i],
инициализирует UART (`uart_port_init`) и зондирует линию (`bt_line_probe`):

| idx | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| baud | 9600 | 19200 | 38400 | 57600 | 115200 | 230400 | 460800 | 921600 |

Фоллбеки: после цикла при `bt_line_probe(0)==0` — **460800** (0xfb0fe2);
при невалидном канале — **9600** (0xfb1312 в `bt_line_probe`, ветка `==2`).

### 3. Смена скорости в рантайме — `j2534_SetConfiguration_uart` (0xfab042)

baud из `arg_2` → `serial_channel_set_config` → `uart_port_init`
для двух UART-каналов (0xfab075, 0xfab07f): **`ser_chan_usb` + `ser_chan_dbg`** —
хост-порт и debug-порт синхронизируются одной командой J2534 SetConfiguration.

## Как пишется BRG

Адрес UART-регистров вычисляется: `A0 = uart_port_base + (reg − u0smr4)`;
имmediate 0x364 встречается только в таблице данных 0xfa0050 (ряд 0x364, 0x2E4, 0x334, 0x324).
Таким образом один и тот же код пишет UART0…UARTN через переключаемую базу.

По данным M32C/85 HM делитель: `BRG+1 = Fosc / (2·16·baud)` (Fosc = 30 МГц):

| baud | 9600 | 19200 | 38400 | 57600 | 115200 | 230400 | 460800 | 921600 |
|---|---|---|---|---|---|---|---|---|
| BRG | 96 (0x60) | 48 (0x30) | 24 (0x18) | 16 (0x10) | 7 (0x07) | 3 (0x03) | 1 (0x01) | 0 (0x00) |

## Замена BT-модуля на CH05 (предзапрограммированный)

Сторона Windows: коннект до CH05 **уже работает** (SPP-сервер «J2534»).
Остаётся только снять AT-зависимость MCU. Карта точек зависимости (в IDB
поставлены комментарии + закладка на 0xfb15be):

| # | Адрес | Что | Патч для CH05 |
|---|---|---|---|
| 1 | `bt_baud_detect` (0xfb0ec2) | ждёт `AT`→OK при автодетекте; иначе 8× таймаут ≈ 28 с → fallback 9600 | CH05 отвечает OK на 460800 **или** форс-baud патчем |
| 2 | 0xfb13c6 и 0xfb112b | `JSR.W bt_at_init` (13 AT-команд конфиг) | `NOP NOP` — конфиг не нужен (CH05 предзапрограммирован) |
| 3 | `sub_FB15BE` (0xfb15be), вызов **каждый J2534 Open** (fab889) | `ATD%s,1101` — исходящий dial; без OK Open вернёт ошибку (fab890) | тело → `MOV.B #0,R0L; RTS` |
| 4 | 0xfb12cb | импульс P2.1 200 мс — reset/enable BT-чипа | проверить EN vs RESET у CH05; если EN — патч 0xfb12cb..fb12db |
| 5 | `bt_rx_read` (0xfb1676) | приём гейтится `ser_boot_state==1` (ставится только после успешного AT-цикла) | след. за патчами 1–3 (или прямая установка флага) |

Архитектурный нюанс: оригинальная модель — **адаптер сам дозванивается**
хосту (`ATD%s,1101`, адрес передаёт хост в Open), т.е. CH-модуль — SPP-клиент.
Для CH05-сервера модель обратная (хост подключается к модулю) — срабатывает
патч 3.

## Замечания

- В коде адресуются только регистры `u0*` (UART0) — мультиплексация портов
  идёт через базу `uart_port_base`; UART1–4 (SFR 0x2E4/0x2E4/0x324/0x334) не встречаются.
- В IDB проставлены: 27 функций, 15 глобальных, 38 комментариев, 2 закладки.
- Отладочная строка `%s   Baud  %9lu\n\r` (0xfa979a) выводит текущий baud.
- Строка `Channel id: 1 - CAN MS, 2 - CAN HS` (0xfa9d73) — CAN-каналы J2534, не UART.
- `TSDiCE64.dll` (хост) — COM-порт J2534 (`Comport=COM12`); BT — отдельный SPP-интерфейс.
