# Чтение bootloader'а DiCE через RFC (задача на паузе)

Статус: **приостановлено** — разбор API почти готов, чтение не запускалось.
Диапазон bootloader-банка в `dice_5_6_2.mot` отсутствует (образ приложения —
только `0xFA0000..0xFD1FF0`), а обработчики RFC-команд лежат именно в нём
(указатели `0xFF96CE..0xFF98A2`), т.е. это недостающий кусок прошивки.

## Что используется

- **`RfcFWDL32.dll`** — RFC-загрузчик/читалка SETEK, **x64** (IDA-база
  поднималась на MCP-порту **13346**). Общается с адаптером **по USB**
  (импорты SETUPAPI: `SetupDiGetClassDevsA` и т.д.), **не по COM**.
  COM3/COM4 — не используются; COM12/COM13 — артефакты сопряжения HC-05.
- Устройство должно быть **свободно**: J2534-приложение (драйвер TSDiCE64)
  должно быть закрыто перед `RfcOpen`.

## API DLL (fastcall x64: rcx, rdx, r8, r9), сверено по дизассемблированию

| Экспорт | RVA | Сигнатура | FID | Примечание |
|---|---|---|---|---|
| `RfcOpen` | 0x1590 | `int (char* name)` | — | открывает устройство; 0 = OK; ставит `byte_1800133B9=1`. Аргумент — **имя устройства** из `RfcQuery` (`"dice-206751@000000000000"`), а **не индекс**: `RfcOpen(0)` → 1, `RfcOpen(1)` → AV (проверено на железе 22.09.2026, см. ниже) |
| `RfcClose` | 0x1190 | `void ()` | — | `[vtable+16]()` |
| `RfcQuery` | 0x10E0 | `int (int a, char* buf, int len)` | — | перечисляет устройства: `sub_1800025A0(ctx, табл=&unk_180013430, &кол-во dword_180013424)`; таблица — массив указателей (шаг 8 B), имена копируются в `buf` |
| `RfcMaxSize` | 0x1D80 | `int (uint16* out)` | 1 | максимальный размер блока передачи (word из ответа) |
| `FwdlRead` | 0x2200 | `int (uint32 addr, uint32 len, void* buf)` | **0x7B** | args: `addr`→req+0, `len`→req+4; из ответа копируются `len` байт (`resp+1`) |
| `FwdlWrite` | 0x2280 | `int (uint32 addr, uint32 len, void* data)` | 0x7C | **не использовать** |
| `FwdlCS` | 0x21A0 | `int (uint32 addr, uint16* out)` | **0x7D** | 16-битная сумма, которую считает **MCU** по диапазону от `addr` |
| `FwdlErase` | 0x2100 | `int (uint32 addr)` | 0x77 | **не использовать** |
| `FwdlProg` | 0x20B0 | `int (uint32 addr)` | 0x78 | **не использовать** |
| `FwdlLock` | 0x2150 | `int (uint32 addr)` | 0x7A | |
| `SysBootloaderVersion` | 0x1F70 | `int (uint8* maj, uint8* min)` | 6 | два байта версии bootloader'а |
| `RfcVersion` | 0x1DD0 | `int (…)` | 7 | версия RFC-стекa |
| `RfcDeviceVersion` | 0x1D00 | — | — | |
| `SysDeviceName` / `SysHardwareVersion` / `SysFirmwareVersion` / `SysUsbProductId` | 0x23A0 / 0x1FE0 / 0x1EB0 / 0x2410 | — | — | |
| `SysReset` | 0x1E60 | — | — | сброс MCU — **осторожно** |
| `SysFirmwareDisable` | 0x2060 | — | — | |

Ответная рамка приходит в `qword_180013418`: `[0]=статус` (0 = OK, иначе
код ошибки), `[1..]=данные`. `sub_180001C60` ждёт event с таймаутом 30 с
(`0x7530`); возвращает 0 при успехе, 0xFD при несовпадении FID, 0xFF при
таймауте, 0xF8 при закрытом устройстве.

## RFC-кадр (из `sub_180001620`)

```
0xB5 | len(LE16) | hdr_cs | FID | payload(len-2) | msg_cs
hdr_cs  = len_lo + len_hi + 0x1E
msg_cs  = 0x69 + FID + Σ payload
```
Проверки на хосте: `ERR_RFC_HCS` / `ERR_RFC_MCS`; неизвестный FID —
`ERR_RFC_FID` (ответ с тем же FID+0xFD? — см. сравнение `byte_1800133A2`).

## Проверено на железе 22.09.2026 (USB, режим приложения)

Вызовы из 64-битного Python (`scripts/rfc_readback.py`), устройство свободно
(DiagApp закрыт), прошивка заводская 5.6.2:

| Вызов | Результат |
|---|---|
| `RfcQuery(0, buf, 1024)` | 0, имя устройства `dice-206751@000000000000` |
| `RfcOpen(0)` | **1** (ошибка) |
| `RfcOpen(1)` | **access violation** (аргумент разыменовывается) |
| `RfcOpen("dice-206751@000000000000")` | **0** (OK) |
| `RfcMaxSize(&u16)` | 0, значение **4200** — RFC-канал жив |
| `FwdlRead(0x7B)` @ 0xFA0000 / 0xFB0EC2 / 0xFA1000 / 0xFB0000 / 0xFC0000, len 16…512 (и с перестановкой аргументов) | **0xFD** у всех, данные не копируются |
| `FwdlCS(0x7D)` @ 0xFA0000 / 0xFB0EC2 / 0xFB15BE / 0xFC0000 | **0xFD** у всех |

Вывод: **в режиме приложения команды доступа к флешу (0x7B read, 0x7D CS)
не выполняются** (0xFD = «несовпадение FID»/ошибка), при этом FID 1 отвечает
нормально. Значит читать флеш можно только в **режиме обновления**, который
активирует `FwdlApp` (кандидат на вход — `SysFirmwareDisable` 0x2060, затем
`FwdlRead`, затем `SysReset`; **не проверялось**, риск: устройство останется
в режиме загрузчика до повторной прошивки).

Практические следствия:

- верификация патча «чтением по RFC» из работающего приложения **невозможна**;
- штатная альтернатива — лог `FwdlApp.exe.log`: после стирания/записи он сам
  делает `FwdlCS`-верификацию и пишет «Device update OK!»;
- поведенческая проверка — `scripts/bt_probe.py`: патченная прошивка отвечает
  по BT, заводская молчит.

### В режиме программирования (prog-mode) чтение РАБОТАЕТ

Во время прерванной прошивки устройство осталось в prog-mode, и тогда:

```
RfcQuery() = 0            -> dice-206751@000000000000
RfcOpen(name) = 0
FwdlRead(0xFA0000, 16) = 0 -> cc 6a a2 fa 00 00 00 00 03 00 00 00 00 00 01 00
```

(в файле на этом месте `cc 6a a2 fa 05 06 ff ff 03 ...` — т.е. видно, что
запись оборвалась на середине: байт сборки `03` уже патченый, а слова
`0xFA0004..07` ещё пустые).

Значит порядок для чтения такой: FwdlApp входит в prog-mode («Restarting
device» в его логе) → `FwdlRead`/`FwdlCS` отвечают → устройство перезапускается.
Замечание: чтение подряд разных адресов в одной сессии нестабильно — на
`0xFB0000` процесс с `FwdlRead` упал нативно (вероятно, состояние устройства
после оборванной прошивки); читать лучше по одному блоку за сессию.

## Сторона MCU (база `dice_5_6_2.mot.i64`, порт 13345)

- Диспетчер команд — **`0xFA2AE2`** (в приложении): `PUSHM A0` + цепочка
  `CMP.B #imm,R0L / JMP.W`: FID 0..8 → `0xFF96CE/0x96F2/0x9708/0x971C/0x9750/
  0x9774/0x9788/0x97A4/0x97BA`; FID `0x77 'w'` → `0xFF97CE` (erase),
  `0x79 'y'` → `0xFF97E2` (read?), `0x7A 'z'` → `0xFF97F6` (lock),
  **`0x7D '}'` → `0xFF980A` (checksum)**, `0x7B '{'` → `0xFF982C` (read),
  `0x7C '|'` → `0xFF9856` (write), `0x7E '~'` → `0xFF9878`,
  `0x7F` → `0xFF98A2`.
- Таблица указателей — `dword_6C8` (RAM), вызов — `JSRI.A` (`0xFA2C65`),
  код возврата < `0x80` → OK, иначе ошибка.
- Сборка исходящих RFC-кадров в MCU: `0xFA2EB1` / `0xFBF74D` (та же
  структура 0xB5/hdr_cs/msg_cs — взаимно проверяются).
- **Все обработчики — в банке `0xFF9xxx`, которой нет в .mot.** Векторная
  зона `0xFFDF0..` в IDB — `0xFF` (не мапится из образа).

## План чтения (на паузе; возобновлять с этого)

1. 64-битный PowerShell + `Add-Type` C# P/Invoke на `RfcFWDL32.dll`.
2. `RfcQuery` → таблица устройств; `RfcOpen(индекс)`; при 0xF8/0xF6 —
   проверить, не занято ли устройство J2534-приложением (закрыть).
3. `SysBootloaderVersion` + `RfcMaxSize` → размер чанка для чтения.
4. Цикл `FwdlRead(addr, len, buf)` по bootloader-банку:
   - известные адреса кода: `0xFF96CE..0xFF98A2+` → читать
     **`0xFF9000..0xFFBFFF`** (8 КБ) на первом проходе;
   - границы уточнить по содержимому (векторы, константы) и/или
     `RfcMaxSize`.
5. Сверка: `FwdlCS` на прочитанных диапазонах (MCU считает сам — можно
   перепроверить целостность чтения).
6. Собрать бинарник, загрузить в IDA (`-b` imagebase `0xFF8000` или по
   факту), дизассемблировать, по именам FID-обработчиков сверить с таблицей
   из п. «Сторона MCU».

## Риски и меры

- Чтение флеша по RFC **безопасно** (FID 0x7B/0x7D — read-only).
- **Никаких** `FwdlErase/FwdlWrite/FwdlProg/SysReset` в рамках задачи.
- `SysReset` (если понадобится после зависшего open) перезапустит MCU —
  адаптер «пропадёт» из J2534-приложения до повторного open.
- Если `RfcOpen` возвращает 0xF6 (`byte_1800133B8==0`, «not initialized»)
  — вероятно, нужен иной порядок (RfcQuery до open) или устройство не в
  RFC-режиме (обычно вход в RFC — через кнопку/команду или при отключённом
  J2534-драйвере; уточнить в документации SETEK).

## Открытые вопросы

- Семантика аргумента `RfcOpen` (индекс из таблицы RfcQuery? — проверить
  на практике; таблица `unk_180013430` — массив `ptr`, шаг 8 B).
- Точные границы bootloader-банка (верх флеша: откуда начинается, сколько
  КБ; M32C/85 — банк-структура, нужен даташит/документация SETEK).
- Нужен ли хендшейк после `RfcOpen` (например, версия/RFC-идентификация)
  — в `sub_1800025A0` (enumerate) и `RfcOpen` на это не похоже, но при
  первом запуске проверить по таймаутам.
