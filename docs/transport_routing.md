# Как DiCE определяет транспорт ответа

Коротко: **роутера/реестра «активного порта» нет**. Каждый физический
транспорт — независимый канал со своими кольцами RX/TX и своим
протокольным состоянием. Ответ уходит **по тому же каналу, на котором пришёл
запрос** — это свойство конструкции, а не результат динамического выбора.

## Канальная абстракция (физический уровень, в .mot)

- Таблица каналов: базовый массив **`0x2677`, шаг `0x63` (99 B)** на канал.
  Поля канала: `ser_chan_enabled` (бит «включён», иначе ст. 9),
  указатели хвост/голова TX (`word_2677`/`2679`), RX
  (`word_2683`/`2685`), флаги (`byte_268D`, `268B`, `268C`, `268F`,
  `2694`, `2699`…), номер UART-порта (`unk_265F`, 0 или 1).
- Управление каналом: `uart_port_init(ch)` (`0xFC0FD2`),
  `serial_channel_reset(ch)` (`0xFC129E`),
  `serial_channel_set_config(ch, …)` (`0xFC131A`),
  `serial_channel_start(ch)` (`0xFC174A`),
  `serial_channel_get_state(ch)` (`0xFC16F4`).
- RX-прерывание UART: RX-кольцо наполняет ISR — общий блок `chan_rx_isr`
  (0xFC1E0C..0xFC1E4F) для каналов 2/3 и `sub_FC1E7E` для канала 0 (BT); байт
  читается из регистра данных UART (`uart_port_base + #u0rb - #u0smr4`) и
  кладётся в RX-кольцо **своего** канала (векторы 0xFAA1B0 — RX BT,
  0xFAA1EC/F0 и 0xFAA1F4/F8 — ch2/ch3).
- TX: продюсер TX-кольца один — `sub_FC154C(chan, &len, data)`; выгрузку
  байта из кольца в `u0tb` делает `chan_rx_append` (0xFC1B92 — имя в IDB
  обманчиво, это не приём).
  > Уточнение 22.09.2026 (по IDB): прежнее описание «RX → `sub_FC1CE6`,
  > допи́ска в кольцо `sub_FC1B92`» неверно. Индексы каналов: `bt=0`,
  > `usb=2`, `dbg=3`. Подробности — в [bridge_patch.md](bridge_patch.md)
  > §1.2–1.4 и [uart_init.md](uart_init.md) («Примитивы канального I/O»).

Следствие: входящий байт «помнит» свой канал по самой природе прерывания
(какой UART сработал), а ответ использует то же протокольное состояние
(STmin, идентификаторы ISO15765, буферы K-line), которое строилось на этом
канале. Двум каналам одновременно «конкурировать» за ответ нечем — общих
глобальных переменных маршрутизации нет.

## Где всё-таки происходит «выбор»

1. **На стороне J2534-хоста** (TSDiCE64.dll): приложение запрашивает
   конкретный протокол (ISO15765 CAN, ISO9141 K-line, …) и физический
   коннектор.
2. **`j2534_SetConfiguration_*`** в MCU (напр. `j2534_SetConfiguration_uart`
   `0xFAB04x`) маппит запрос на **индекс канала** и поднимает его:
   `serial_channel_reset → serial_channel_set_config → uart_port_init →
   serial_channel_start` (наблюдается в кросс-референсах всех
   `serial_channel_*` — вызовчики: `j2534_SetConfiguration_uart`,
   `iso15765_can_init`, `kline_iso9141_pump`, `iso9141_kline`,
   `bt_channel_start` и др.).
3. **Bluetooth-канал** поднимается отдельным путём
   (`bt_channel_start` `0xFB16A0`, `bt_at_*`, AT-пробы `bt_line_probe` /
   `bt_boot_atz_probe` / `bt_baud_detect` — зона CH05-патча).
4. **Обнаружение физического наличия линии** — `sub_FBDE88`: читает пины
   **P1.7 / P3.5 / P1.1** (`BTST` → `SCGEU` в `R0L/R1H/R1L`), сравнивает с
   сохранённым состоянием `byte_23CD` / `byte_263B` / `byte_263C`;
   изменение учитывается, только если канал включён
   (бит 4 в `byte_203` / `byte_283`). Это детект «что подключено»,
   а не выбор маршрута.

## RFC-протокол (загрузка/чтение прошивки)

Машина состояний `0xFA2C8E` (статус в `byte_BE5`, 0..5) работает строго
**request/response по одному потоку**: байты RX берутся из
`unk_FFA2F2`, байты TX уходят через `unk_FFA24E`. Понятия «канал» внутри
нее нет — транспорт, на котором лежит этот поток, зафиксирован уровнем
ниже. Ответ (в т.ч. на FID 0x7B read / 0x7D checksum) возвращается по тому
же потоку, что и запрос.

## Оговорки

- Обёртки физического I/O RFC-потока (`0xFFA24E`, `0xFFA2F2`) и сами
  обработчики RFC-команд лежат в **отсутствующем банке `0xFF9xxx`**
  (bootloader, см. `rfc_bootloader_read.md`) — точное привязывание
  RFC-потока к конкретному UART-порту видно только после прочтения банка.
- Полный список каналов и их привязка пинов ↔ UART-порты частично
  задаётся в том же отсутствующем банке и в таблицах RAM (`uart_port_base`).
